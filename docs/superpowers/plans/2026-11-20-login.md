# Login e controle de acesso — plano de implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Só entra no sistema quem tem login e senha; o admin vê tudo e libera menus, aprova/recusa recepcionistas numa tela de Acessos.

**Architecture:** Sessão guardada no banco (tabela `sessoes`, hash do token) e entregue num cookie httpOnly `sessao`. A API protege cada rota com dependências do FastAPI (`usuario_logado`, `exigir_menu`, `exigir_admin`). O Next tem um `proxy.ts` como primeira barreira, o layout lê `/api/eu` no servidor repassando o cookie e desenha o menu só com os itens liberados.

**Tech Stack:** FastAPI + SQLAlchemy 2 + Pydantic 2 + pytest (SQLite nos testes) · Next.js 16 (App Router) + TS + Tailwind 4.

**Spec:** `docs/superpowers/specs/2026-11-20-login-design.md`

## Global Constraints
- Menus liberáveis, exatamente: `agenda`, `clientes`, `barbeiros`, `servicos`, `historico`, `aparencia`. "Acessos" nunca é liberável; admin tem todos.
- Admin padrão: login `admin`, senha `123`, criado na subida da API se não existir nenhum admin.
- Login: 3–30 caracteres, só `a-z 0-9 . _`, guardado e comparado em minúsculas.
- Senha nova: mínimo 4 caracteres, máximo 72.
- Senha com `hashlib.scrypt` (n=2**14, r=8, p=1, dklen=32) + sal aleatório de 16 bytes, guardada como `scrypt$<sal hex>$<hash hex>`; comparação com `hmac.compare_digest`. Sem dependência nova.
- Cookie: nome `sessao`, httpOnly, SameSite=Lax, path `/`, max_age 12 h (43200 s), sem `secure` (roda em http://localhost). Token `secrets.token_urlsafe(32)`; no banco só o sha256 hex.
- Mensagens (exatas): login errado → 401 "Login ou senha incorretos."; bloqueada → 403 "Seu acesso está bloqueado. Fale com o administrador."; sem sessão → 401 "Faça login para continuar."; sem o menu → 403 "Você não tem acesso a este menu."; senha atual errada → 422 campo `senha_atual` "Senha atual incorreta."; login repetido → 409 campo `login` "Já existe um usuário com esse login.".
- Bloquear (`ativo=false`) e trocar a senha de uma recepcionista apagam as sessões dela.
- Ler clientes/barbeiros(+foto)/serviços: qualquer logado. Gravar: o menu. Agendamentos: `agenda`. Histórico: `historico`. Aparência: GET e GET logo abertos; gravar: `aparencia`. `/` e `/docs` abertos.
- Fontes não mudam; telas novas usam os componentes da casa (Topo, Secao, Campo, Botao, Chave) e os tokens de cor do tema.
- Comentários e textos em português, no tom do projeto.

## Review Focus
1. **Cookie velho/inválido** (sessão vencida, recepcionista bloqueada): o `proxy.ts` deixa passar porque o cookie existe; o layout não acha usuário e manda pra `/login`. Não pode virar laço de redirecionamento — o proxy **não** tira ninguém de `/login`; quem manda um usuário válido de `/login` pra dentro é a própria página/layout depois de conferir `/api/eu`. Teste: com cookie `sessao=lixo`, abrir `/agenda` termina em `/login` e a tela de login aparece.
2. **Bloqueada no meio do uso:** a próxima chamada da API volta 401 e o front leva pra `/login` (tratado no `requisitar`). Teste backend: bloquear → a sessão antiga dá 401 em `/api/eu`.
3. **Admin não se tranca pra fora:** `/api/usuarios/{id}` com id de um admin → 404 (só mexe em recepcionista). Teste.
4. **Login com maiúscula/espaço** ("  Admin ") entra; criar "Maria" e "maria" → 409 no segundo. Teste.
5. **Datas no SQLite** voltam sem fuso: comparar `expira_em` com "agora" não pode estourar `TypeError` nem aceitar sessão vencida. Teste com sessão vencida (ajustar `expira_em` no banco pro passado → 401).

### Task 3: Login no site (proxy, layout, menu, tela de login)

**Files:**
- Create: `frontend/src/proxy.ts`, `frontend/src/lib/servidor.ts`, `frontend/src/components/UsuarioContexto.tsx`, `frontend/src/components/GuardaDeMenu.tsx`, `frontend/src/app/login/page.tsx`, `frontend/src/app/login/layout.tsx` (metadata "Entrar")
- Modify: `frontend/src/lib/api.ts`, `frontend/src/lib/tipos.ts`, `frontend/src/app/layout.tsx`, `frontend/src/app/page.tsx`, `frontend/src/components/MenuLateral.tsx`

**Interfaces:**
- Consumes: `POST /api/login`, `POST /api/logout`, `GET /api/eu` (Task 1).
- Produces:
  - `tipos.ts`: `type Menu = "agenda" | "clientes" | "barbeiros" | "servicos" | "historico" | "aparencia"`; `MENUS: { menu: Menu; nome: string; caminho: string }[]` na ordem do menu lateral (Agenda, Clientes, Barbeiros, Serviços, Histórico, Aparência); `interface UsuarioLogado { id; login; tipo: "admin" | "recepcionista"; menus: Menu[]; senha_padrao: boolean }`; `primeiroCaminho(usuario: UsuarioLogado): string | null` (admin sem menus nunca acontece; recepcionista sem menu → null)
  - `api.ts`: `requisitar` manda `credentials: "include"`; resposta 401 fora de `/login` e fora da própria chamada de login → `window.location.href = "/login"` (só no navegador). Funções `entrar(login, senha)`, `sair()`, `pegarEu()`.
  - `servidor.ts` (só servidor): `lerUsuario = cache(async () => UsuarioLogado | null)` — fetch `/api/eu` com `headers: { cookie: (await cookies()).toString() }`, `no-store`, timeout 1500 ms; qualquer falha → null.
  - `UsuarioContexto.tsx`: `ProvedorDeUsuario({ usuario })` + `useUsuario(): UsuarioLogado` (client).
  - `GuardaDeMenu`: client; pelo `usePathname`, se o caminho é de um menu que o usuário não tem → `router.replace(primeiroCaminho)`; `/acessos` só admin; `/senha` todo mundo.
- Comportamento:
  - `proxy.ts`: sem cookie `sessao` e caminho ≠ `/login` → redirect `/login`. **Nunca** redireciona saindo de `/login`. Matcher exclui `_next`, arquivos com extensão (favicon, fontes, imagens). Conferir a convenção do Next 16 no `node_modules/next` instalado (arquivo `proxy.ts`, função exportada `proxy`) antes de escrever.
  - `layout.tsx`: lê aparência e usuário em paralelo. Sem usuário → desenha só `{children}` dentro do `ProvedorDeAparencia` (tela cheia, fundo papel), sem menu. Com usuário → como hoje, com `ProvedorDeUsuario`, `GuardaDeMenu` e o menu. O layout não sabe o caminho; quem manda o anônimo pra `/login` é o proxy (sem cookie) e, com cookie inválido, a página: `GuardaDeMenu` não existe sem usuário, então crie no layout sem usuário um pequeno client `IrParaLogin` que, se `pathname !== "/login"`, faz `window.location.replace("/login")`.
  - `/login/page.tsx` (client): se `pegarEu()` responder ok ao montar → `window.location.replace("/")`. Cartão centralizado no estilo da casa: logo (se houver), linha de cima e nome da Aparência, campos Login e Senha (`autoComplete` username/current-password), botão "Entrar", erro da API embaixo. Sucesso → `window.location.replace("/")` (recarrega pra o layout reler).
  - `app/page.tsx` (servidor): `lerUsuario()`; sem usuário → `redirect("/login")`; com `primeiroCaminho` → redirect pra ele; recepcionista sem menu → página com o aviso "Nenhum menu liberado ainda. Fale com o administrador." e botão Sair.
  - `MenuLateral`: itens filtrados por `usuario.menus`, + "Acessos" (`/acessos`) no fim pro admin. Rodapé (preso embaixo): login do usuário, link "Trocar senha" (`/senha`) e botão "Sair" (`sair()` e `window.location.replace("/login")`).
